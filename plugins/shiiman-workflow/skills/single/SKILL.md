# Single Flow

シングルエージェントで計画書またはタスク説明を順次実装する開発フロー。

フラグは不要。タスクを伝えれば、git の状態・発話内容から実行条件を自動判断し、曖昧な点だけ確認する。

## Help

`$ARGUMENTS` に `--help` が含まれる場合、以下を表示して終了:

```text
shiiman-workflow:single - シングルエージェント開発フロー

概要:
  計画書またはタスク説明を 1 エージェントで順次実装する。
  実装条件（Issue/PR・計画書・ブランチ・git）はフラグ不要で自動判断し、
  曖昧な点だけ確認する。

使用方法:
  shiiman-workflow:single [タスク説明]
  shiiman-workflow:single --help

オプション:
  --help  このヘルプを表示

例:
  shiiman-workflow:single                          # 既存計画書から実装（あれば）
  shiiman-workflow:single "ログイン機能を追加"      # タスク説明から実装
  shiiman-workflow:single "認証を実装して PR まで"  # 実装・コミット・push・PR 作成
  shiiman-workflow:single --help                   # ヘルプを表示

指定の伝え方（フラグの代わり）:
  - 「計画を立ててから」  → 計画書を作成してから実装
  - 「ブランチで」        → worktree ではなくブランチを作成
  - 「PR まで」           → コミット・通常の push・PR 作成まで実施
  - 「Issue と PR まで」   → Issue 作成も含めて実施
  - 「コミットだけ」      → 検証後にコミットし、push・Issue・PR は作成しない
```

## 前提条件

- `gh` コマンドが利用可能
- `gh auth status` が成功する（GitHub CLI 認証済み）

## 起動時の自動判断（フラグの代わり）

ユーザーにフラグを入力させない。以下を順に決定する。**発話・タスク説明に明示があればそれを最優先**し、明示がなければ自動判断、それでも曖昧な項目だけ後述の手順で確認する。

| 項目              | 既定       | 判断ルール                                                                                |
| ----------------- | ---------- | ----------------------------------------------------------------------------------------- |
| git / no-git      | 自動       | `git rev-parse --is-inside-work-tree` 成功なら git。失敗なら no-git（ブランチ作成を省略） |
| worktree / branch | worktree   | 「ブランチで」「worktree なし」等の発話があれば branch                                    |
| 計画書の扱い      | 後述の判定 | 「計画を立てて」「plan で」→ 計画書作成。タスク説明あり → 直接。なし → 既存計画書を探索   |

### 許可された完了範囲

現在の依頼と既存の許可から、操作ごとに実行範囲を判断する。

- 実装だけの依頼: 実装・レビュー・検証を行い、コミットや Issue・PR を作るかの追加質問はせず終了する。
- コミットだけの依頼: チェック後に対象変更をコミットする。push や Issue・PR 作成は行わない。
- PR 作成の依頼: 必要な実装・検証・対象変更のコミット・通常の feature branch push を完了して PR を作成する。Issue は依頼されているか、許可済みのワークフローで必要な場合だけ作成する。
- Issue 作成の依頼: 依頼された Issue と明示された後続操作だけを行う。必要に応じて確認済みの既存 Issue を参照する。
- 「push しない」などの明示的な制約を優先する。範囲を黙って広げず、具体的な阻害要因を報告する。

許可済みの操作に `--no-confirm`、計画承認、完了時の再承認を要求しない。後続の仕上げ手順も個別に許可された操作だけを実行し、依頼されていない手順は省略する。重要な範囲変更、破壊的操作、高影響操作が発生する場合は許可を再確認する。

### git の状態判定

```bash
git rev-parse --is-inside-work-tree >/dev/null 2>&1
```

- 成功 → git モード（ブランチ/worktree を作成）
- 失敗 → no-git モード（ブランチ作成を省略し、実装とサマリー出力のみ）

### 計画書の扱いの判定

1. 「計画を立ててから」等の依頼がある → **計画作成**: `.claude/plans/` に計画を保存する。実装も依頼されていれば説明後に続行し、計画承認を明示的に求められた場合や重要な未解決の判断がある場合だけ待機する
2. タスク説明がある → **直接実行**: タスク説明をそのまま実装の指針にする（計画書を作らない）
3. タスク説明なし → **既存計画書**: 最新の計画書を読み込む

```bash
ls -t ~/.claude/plans/*.md 2>/dev/null | head -1
```

計画書が見つからなければ「タスク説明を教えてください。または計画を立ててから実装することもできます」と案内して終了。

## 実行フロー（共通）

```text
[Issue 作成が許可済みの場合のみ] Issue 作成 →
ブランチ/worktree 作成 → 実装 → セキュリティチェック＆自己レビュー →
[許可済みの操作のみ] コミット → push → PR 作成 → 完了報告
[連携なし] コミットメッセージ出力で終了
```

### ステップ A: 許可されている場合だけ Issue を作成

`shiiman-github:issue-create` スキルのワークフローに従い、`--no-confirm` オプションで Issue を作成する。タスク内容を 50 文字以内のタイトルにし、本文は「## 概要 / ## タスク（チェックボックス）/ ## 完了条件」で構成する。ラベルは内容に応じて `enhancement` / `bug` / `documentation` / `improvement` を付与。

作成された Issue 番号を後続ステップで使う。

### ステップ 1: ブランチ / worktree 作成

git モードのみ実施（no-git モードはスキップ）。

- worktree（既定）: `shiiman-github:worktree-create` スキルのワークフローに従う
- ブランチ: `shiiman-github:branch-create` スキルのワークフローに従う
- 確認済みの関連 Issue がある場合だけ Issue 番号を渡し、なければタスクに基づくブランチ名を使う。

ユーザーがベースブランチを明示した場合はそちらを優先する。

### ステップ 2: 実装

計画書またはタスク説明に基づいて実装する。

1. 必要なファイルを特定
2. コード変更を実施
3. 動作確認（可能な場合）
4. 更新が許可された確認済みの Issue について、実際に完了したタスクだけチェックボックスを更新する。

### ステップ 3: セキュリティチェック＆自己レビュー

```bash
git status
git diff
```

- 機密ファイルを検出したら警告: `.env*`（環境変数）、`*.pem` / `*.key`（秘密鍵）、`credentials.json`（認証情報）、`node_modules/` / `vendor/`（依存）
- 自己レビュー観点: コード品質・命名規則 / セキュリティ（OWASP Top 10）/ パフォーマンス（N+1・メモリリーク）

### ステップ 4: 検証後に許可範囲内で続行

検証済みの変更とチェック結果を進捗で報告し、許可された仕上げの操作を続ける。差分やコミットメッセージの承認だけを理由に停止しない。具体的なリスクや未解決の範囲判断で確認が必要な場合は、確認可能な成果を準備してその判断だけを質問する。

## 仕上げ

### 許可された仕上げ操作

以下のうち許可された操作だけを実行する。同じ内容の再承認は不要。

1. 更新が許可された Issue のうち、実際に完了したタスクだけをチェックする。未完了タスクを完了にしない。
2. コミット: `shiiman-git:add-commit` スキルのワークフローに従い、`--no-confirm` オプションでコミットする
3. push または PR 作成が許可されている場合は、remote・送信先の branch・送信対象のコミットを確認して `git push -u origin {branch}` で対象 feature branch を push する。この許可だけで force-push、デフォルトブランチへの push、無関係な作業の公開は行わない。

4. PR 作成: `shiiman-github:pr-create` スキルのワークフローに従い、`--no-confirm` オプションで PR を作成する。日本語で概要・変更内容・検証結果を記載する。`Closes #N` は確認済みの関連 Issue がある場合だけ含め、なければ Issue 欄を省略する。
5. 実際に完了した操作だけを報告し、未実行の Issue・PR の項目は省略する。

   ```text
   ## 開発フロー完了

   ### 作成された Issue
   - #{issue番号}: {タイトル}

   ### 作成されたブランチ / worktree
   - {ブランチ名}
   - パス: {worktree のパス}（worktree モード時のみ）

   ### 作成された PR
   - PR #{pr番号}: {タイトル} / {pr_url}

   PR がマージされると Issue #{issue番号} は自動的にクローズされます。

   ### worktree クリーンアップ（worktree モード時のみ）
   PR マージ後、`/shiiman-git:worktree` で gtr rm または gtr clean を実行してください。
   ```

### Issue/PR 連携なし（軽量）

実装だけの依頼では、変更と検証結果を報告して終了し、コミット・push・Issue・PR 作成は行わない。コミットだけの明示的な依頼では、検証して対象変更をコミットし、結果を報告する。任意の後続操作を追加で質問しない。

```text
## 実装完了

### 作成されたブランチ / worktree（git モード時のみ）
- {ブランチ名}
- パス: {worktree のパス}（worktree モード時のみ）

### 変更サマリー
{git diff --stat}

### 推奨コミットメッセージ
{リポジトリとグローバル指示に従う Conventional Commits メッセージ}

### 検証結果
{実行したチェック・結果・残課題}
```

## 重要な注意事項

- ✅ ユーザーにフラグを入力させない（git・worktree/branch・計画書・Issue/PR を自動判断、曖昧なら確認）
- ✅ 計画書作成は「計画を立ててから」と依頼されたときのみ実施
- 許可済みの仕上げ操作は再確認せず続行する。
- ✅ 機密ファイルを警告・除外する
- コミットの規約はリポジトリとグローバル指示に従い、未対応の設定キーを仮定しない。
- ❌ デフォルトブランチで直接作業・コミットしない
- 外部操作や Git の仕上げ操作は、それぞれ許可された範囲内だけで実行する。
